# Як ми пишемо статті

Практична інструкція для матеріалів PLITKA Analytics. Складена після фінальної вичитки статті про проєкт 677 «Лада» — усі приклади нижче реальні, з правок у тому тексті.

---

## 1. Голос: результат, а не процес

Стаття — це **підсумок розслідування**, а не його стенограма. Читач приходить по знання, а не по те, як ми до нього дійшли. Робота з джерелами відбувається до публікації; у текст потрапляє тільки результат.

Кухня майже завжди пролазить через одні й ті самі звороти. Ось із чим боротися:

| Заборонено | Замість цього |
|---|---|
| «Зберімо всі описи в одному місці, бо поодинці кожен вводить в оману» | одразу викласти, що каже кожне джерело |
| «І ще один ключ, без якого все читається неправильно» | подати сам факт прямим твердженням |
| «Варто чесно позначити межу знання» | «Профільні довідники цього не підтверджують» |
| «Фіксуємо це як розбіжність» | «Приписка лишається невизначеною» |
| «Тут варто зняти удавану розбіжність між джерелами» | «Це один і той самий агрегат» |
| «Дані неверифіковані, але узгоджуються з…» | або подати як опис, або не подавати |
| «Красномовна деталь:», «Прикметно, що…», «Найпоказовіше — саме тут» | прибрати, факт говорить сам |
| «Це не оцінка аналітиків і не наш висновок» | «Це позиція конструкторського бюро» |
| «А тепер найважливіше для нашого циклу» | звичайний заголовок розділу |
| «Там, де цифри розходяться, розбіжність — сама по собі інформація» | прибрати, це методологічна ремарка |

**Правило перевірки.** Якщо речення можна почати словами «ми дізналися, що…» або «зверніть увагу, як ми…» — воно про нас, а не про предмет. Переписати.

**Виняток.** Пряма вказівка на межу знання доречна, коли вона змінює висновок читача: «Незалежних підтверджень цьому немає» після гучної заяви — це факт про стан джерел, а не роздум про нашу роботу.

## 2. Розбіжності між джерелами

Це серцевина OSINT-матеріалу, і подавати її треба як **готове зіставлення**, не як міркування вголос.

- Числові розбіжності — у таблицю з колонками за лініями джерел. Заголовок колонки називає джерело, а не «варіант 1».
- Текстові — одним абзацом: що каже A, що каже B, і що з цього випливає.
- Якщо є пояснення розбіжності — дати його прямо: «Клаб-С і «Калібр» — те саме сімейство під різними назвами».
- Якщо пояснення немає — сказати це одним реченням і не розводити: «Чому офіційне повідомлення називає «Онікс», лишається незрозумілим».
- Ніколи не подавати суперечливі дані як однозначні. Але й не перетворювати кожну розбіжність на подію.

## 3. Атрибуція

- Кожне фактичне твердження має покликання на джерело `[N]`.
- Перед публікацією: жодного битого й жодного осиротілого джерела (кожне зі списку має мінімум одне покликання в тексті).
- **Анонімні джерела** — форуми, Telegram-канали, коментарі — не подаються як факт. Або підтверджуються профільним джерелом, або йдуть із явною вказівкою на характер джерела, або не йдуть.
- Не називати форумну дискусію «профільними виданнями» чи «інсайдами». Це підставляє видання, якщо теза не підтвердиться.
- Дані російських і довідкових джерел позначати як **заявлені**, а не як встановлені.

## 4. Термінологія

- **Одиниці флоту — «кораблі» й «човни», ніколи «корпуси».** Не «три корпуси серії», а «три човни серії». Виняток: «корпус» у конструктивному значенні — міцний корпус, обводи корпусу, однокорпусна архітектура.
- Перед публікацією прогнати `grep -i "корпус"` і перевірити кожен збіг.
- Русизми: `торпедопогрузочний` → **торпедонавантажувальний**, `вигородка` вживати обережно й лише в технічному контексті.
- Апостроф: **досьє**, а не «дос'є». Перевіряти `п'ять`, `об'єднання`, `інтерв'ю`, `з'єднання`.
- Проєкт, проєкція, проєктувати — через «є».
- Звертання до читача — без наказового способу однини. Не «розгорни картку», а нейтрально.

## 5. Ілюстрації

- **Щільність.** Орієнтир — одне зображення на 400–500 слів, і рівномірно по розділах. Якщо в одному розділі їх більше п'яти — перекіс.
- **Кожне робить свою роботу.** Два розрізи того самого човна поспіль читач гортає не дивлячись. Залишати те, що показує різне: точний кресленик із легендою, об'ємний вигляд, деталь.
- **Рендери й візуалізації** позначати в підписі як проєктні, а не видавати за фото.
- **Підпис** пояснює, що саме бачить читач і чому це важливо, а не дублює alt. Наприкінці — джерело й умова публікації.
- **Заглушки** `[ джерело й умова публікації ]` допустимі в роботі, але **жодної не має лишитися перед публікацією**.
- Імена файлів — **латиницею, без пробілів**: `rubka-foto.jpg`, не `Схема 2.jpg`. Кирилиця в URL кодується у відсотки й ламається на частині CDN.
- `alt` — описовий, для незрячих: що зображено, а не назва файлу.
- Широкі креслення — `className="fig fig--bleed"`, інакше підписи нечитні.
- Нумеровані легенди — `<ol className="fig-legend">` усередині `<figure>`.

## 6. Структура

- `<h2>` з `<span className="h2-num">` — короткий ярлик зліва, тема справа.
- `callout` — блок із висновком або переліком; `callout--warn` — там, де є суперечність або застереження.
- `aside-note` — коротка технічна ремарка на полях.
- `qtbox` — пряма мова з атрибуцією.
- `dossier-card` — досьє на одиницю флоту.
- `term` з `data-def` — підказка для терміна, який читач може не знати. Не зловживати: два-три на статтю.
- Не робити три блоки про одне питання. Якщо тема повертається втретє — звести в один.

## 7. Чекліст перед публікацією

```bash
npx prettier --write "src/app/(main)/articles/<slug>/page.tsx"
npx tsc --noEmit
npm run build
grep -i "корпус" src/app/\(main\)/articles/<slug>/page.tsx
```

Далі вручну:

- [ ] жодної заглушки `[ … ]` у підписах і в підвалі
- [ ] дата в підвалі відповідає стану матеріалу (`оновлено <дата>` для суттєвих доповнень)
- [ ] час читання в `metaline` і `readingTime` у фронтматері збігаються з обсягом (слова ÷ 200, округлення вгору)
- [ ] джерела: немає битих і осиротілих
- [ ] усі зображення лежать у `public/articles/<slug>/`, невикористаних файлів у теці немає
- [ ] англійська версія в `content/articles/en/` синхронізована або свідомо відкладена
- [ ] прочитати текст суцільно й вилучити мета-мову за розділом 1
